# codex_desktop_chat：原生 App 的 Chat 多会话附件工具

版本 1.0.0。权威源码在本目录，Python 导入根为其父目录。使用已经登录的 `com.openai.codex` App 中的 **聊天（Chat）**，不是 Codex CLI/编程任务模型，也不是 Chrome 网页。

## 范围

已实现 Python 同步接口及机器可读 CLI。每个会话默认通过原生“新建窗口”创建独立窗口，绑定原生窗口编号和 App PID。**不同窗口生成并行；新建、模型菜单、输入、发送等界面操作共享跨进程短锁。** 收取只在读取时短暂持锁，等待时不持锁。最多20个 App 窗口（包含用户已有窗口），不盲关他人窗口；这不是网页页池配置。

本版实现文本和本地文件附件，`files` 接收最多10个绝对路径，文件面板在所属窗口逐个精确选择。两路独立会话各带不同PNG已完成真实读取与完整收取；PDF等其他类型尚未实机验收。不接入 paper 常驻制卡，不恢复 Qwen 或历史任务，不自动切换模型/通道。不处理验证码，不自动登录，不绕过账户或模型额度。

## 环境

- macOS 可见桌面，App 已启动、已登录，辅助功能权限已给实际运行进程/宿主。
- Python 3.11+（标准库，无 pip 运行依赖）。首次编译需要 `/usr/bin/swiftc` / Xcode Command Line Tools。
- 原生读取器 `native.swift` 通过 Apple Accessibility/CoreGraphics 实现，使用 Unicode 键盘事件和按语义控件位置核对的原生鼠标点击，不使用系统剪贴板、按标题/论文定制或网页 CDP。
- 前台操作需调用方明确传入 `foreground=True` / CLI `--foreground`。它会激活目标窗口；用户同步切换 App/窗口或输入时，检查失败停止，不保证完全后台控制。

| 配置 | 读取时机 | 默认 |
| --- | --- | --- |
| `CODEX_CHAT_STATE_DIR` | 会话构造 | `~/Library/Application Support/codex-desktop-chat`；只放本工具回执，建议调用方指定绝对目录 |
| `CODEX_CHAT_NATIVE_HELPER` | backend 构造 | 未设置时按源码 SHA-256 在系统临时目录编译缓存；可指定已审查的预编译读取器 |
| `PYTHONPATH` | Python 启动 | 加入包父目录，如 `../../paper` |

源码不猜调用方当前目录。回执包含实际问题、回答及指纹，是私有运行数据；不要提交到 Git。临时二进制只保留源码指纹命名的编译缓存，不复制登录态。

## 单轮调用

```python
from codex_desktop_chat import ask_once

answer = ask_once(
    "请用三句话解释知识图谱。",
    foreground=True,
    state_dir="/absolute/private/desktop-chat-receipts",
    answer_timeout=900,
)
```

返回完整回答字符串。默认精确 GPT-6 / High；选择 GPT-5.6 Sol 必须显式指定 `model="GPT-5.6 Sol"`，没有额度触发的隐式换模型。High 已不符时停止，请在 App 中调整；不会把其它强度伪称为 High。

## 会话、提交和收取

```python
from codex_desktop_chat import ChatGPTDesktop

with ChatGPTDesktop(foreground=True, state_dir="/absolute/private/desktop-chat-receipts") as chat:
    receipt = chat.submit("请解释这个概念。")
    # 此时释放界面提交锁，模型继续生成。
    answer = chat.collect(receipt, answer_timeout=900)
    # 同一窗口可以在完整收取之后继续追问。
    second_answer = chat.ask("再给一个例子。")
    status = chat.status()
```

`create_session(provider="codex-chat", **kwargs)` 返回同一接口。公开方法：`start_new_chat()`、`verify_settings()`、`status()`、`submit(prompt, files=None, *, upload_timeout=180)`、`collect(receipt_or_id, answer_timeout=900)`、`ask(prompt, files=None, answer_timeout=900, *, upload_timeout=180)`。

每个会话最多一个未收取请求。文本上限31500个 UTF-16 单元；默认每10秒检查，`poll_interval` 可设1–60秒。输入在发送前必须逐字匹配（只兼容 Accessibility 自带的一个尾部换行）。工具附加唯一请求身份注记，原问题与实际发送文本分别保存 SHA-256，不上传旧回答。

发送前落盘 `submitting`；之后只凭唯一正式用户消息核对发送。回答需精确请求锚点、原 PID/窗口编号、App 的“回答已完成”、无停止按钮以及连续两次相同全文；先原子落盘回答和 hash 再返回。`scientific_verified=false`、`production_contract_complete=false`；文本收取成功不代表科学验收。

### 多窗口并行

先建立两个独立会话，分别 `submit()`，再通过线程池并行 `collect()`。不持有等待生成期间的全局锁。

```python
from concurrent.futures import ThreadPoolExecutor
from codex_desktop_chat import ChatGPTDesktop

with ChatGPTDesktop(foreground=True, state_dir=STATE_DIR) as a, \
     ChatGPTDesktop(foreground=True, state_dir=STATE_DIR) as b:
    ra = a.submit("请读取A的附件。", files=["/absolute/A.pdf", "/absolute/A.png"])
    rb = b.submit("请读取B的附件。", files=["/absolute/B.pdf"])
    with ThreadPoolExecutor(max_workers=2) as pool:
        fa = pool.submit(a.collect, ra)
        fb = pool.submit(b.collect, rb)
        answer_a, answer_b = fa.result(), fb.result()
```

会话对象本身不要同时从多个线程提交/操作。窗口编号唯一且不跨 App 重启恢复；App 重启、窗口关闭或对话被用户切换均需人工核对。多窗口生成不等于能突破服务端额度。

## 重启后仅收取

保留原窗口和回执目录，用回执中的窗口编号恢复；不得开新窗口重发。

```python
with ChatGPTDesktop(new_chat=False, window_id=receipt["window_id"],
                    state_dir=STATE_DIR) as chat:
    answer = chat.collect(receipt["id"], answer_timeout=900)
```

`new_chat=False` 不改模型、不导航。恢复时要求原 App PID、窗口编号和完整问题指纹一致；只接受已提交/不确定回执。退出上下文不关闭窗口、不取消生成，也不清掉待收取标记。已完成回执可重复读取，先检查回答 hash。

## CLI

```bash
# 状态检查：不新建、不发送、不调整模型
PYTHONPATH=../../paper python3 -m codex_desktop_chat status

# 向新窗口发送指定 UTF-8 文件中的问题，并收取回答
PYTHONPATH=../../paper python3 -m codex_desktop_chat ask \
  --prompt-file /absolute/prompt.txt --state-dir /absolute/private/desktop-chat-receipts --foreground

# 只提交，stdout 返回回执；之后仅收取原窗口
python3 -m codex_desktop_chat submit --prompt-file /absolute/prompt.txt \
  --state-dir /absolute/private/desktop-chat-receipts --foreground
python3 -m codex_desktop_chat collect --receipt-id <32位回执ID> \
  --state-dir /absolute/private/desktop-chat-receipts
```

成功 stdout 为单个 JSON，退出码0；接口失败 stdout 同样单个 JSON，退出码2，包含 `code`、`receipt_id`、`may_have_sent`。命令参数错误由 argparse 输出 stderr / 退出2。问题通过文件/stdin协议传输，不拼接 shell 命令。程序化输入参数见 `input.schema.json`；这份 schema 是调用契约，不是已注册远程 MCP 服务。

## 超时、保护与限制

- `answer_timeout` 是收取阶段墙钟预算；不覆盖 App 启动、首次编译、设置与输入。单次原生读取与锁等待有自己的上限，因此可能略晚返回。
- `answer_timeout`、`submission_unknown`、`native_timeout`、回执/窗口变更均不返回部分回答、不自动重发。异常携带回执 ID；可能已发时保持原窗口，只核对原请求。
- 输入未成功时会保留草稿并记 `not_sent`，不能盲目抹掉已有输入。用户草稿、正在生成和未收取回执阻止新建/复用同一窗口。
- 回执损坏会阻止该目录的执行；未知回执须人工核对，不提供“一键强制清空”。
- 目前要求中文界面“聊天/工作、选择模型、高”等原生标签；界面变化会明确失败。
- 会话靠原生 AX 窗口身份（CFHash，同一 PID 内核对唯一）+PID+唯一完整请求指纹绑定，尚无正式 ChatGPT conversation ID。不要把 App 内部 `app://` 地址当唯一正式会话 URL。当前未达到主文献制卡通道的全部生产合同，不默认接入。
- 完成后的窗口默认保留，可继续追问；不会暗中关闭用户窗口。大量单次 `ask_once` 调用应受20窗口上限约束，或复用已收取的会话对象。自动关闭和常驻页池另需实际验证。

## 0.2.0 附件契约与实测限制

- `files`：列表/元组，0–10个可读普通文件的绝对路径；文件名（不区分大小写）必须唯一。工具本地保护限额每个1–64MiB、总计128MiB，这不是网站额度。文件类型由App判断，不保证所有扩展名可用。
- 先在私有回执目录 `inputs/<receipt_id>/` 保存不可变输入副本及 SHA-256，原文不改写；副本从对应原生文件面板选择。副本和回执供故障核对，完成后目前保留，调用方需按自己的留存策略管理，不能删除未收取/未知请求。
- 文件面板新建/选择持短UI锁，上传进度等待不持锁。每个会话上传和生成独立，其他会话可继续操作/生成。默认 `upload_timeout=180` 秒（全部附件共用，1–3600）；预算不含准备复制和输入，原生操作自身仍有有界超时。
- 需要附件名集合一致、无上传进度/错误、发送控件可用且连续两次稳定才继续。发送前再次核对输入、模型、附件副本哈希；原生助手在实际点击前再核对附件集合和进度，不能靠“发送按钮可点”判断上传完成。
- 正式回执同时核对唯一原提示与同一用户消息区域的附件证据；文档核对名称，匿名图片核对数量，并关联先前上传就绪的不可变图片字节/名称及发送前原生检查记录，不借用助手回复中的文件名。证据不确定记 `unknown`，只查原窗口，不跨窗口重发。原回答科学标志继续为 false。
- `attachment_upload_failed` / `attachment_quota` / `attachment_timeout` / `file_picker_unavailable`：保留窗口、草稿、附件与回执，明确消息未发送时记 `not_sent`；不自动重试、清除草稿或换模型。已有附件不会自动移除。

```bash

  --prompt-file /absolute/prompt.txt --file /absolute/A.pdf --file /absolute/A.png \
  --upload-timeout 180 --state-dir /absolute/private/receipts --foreground
```

## 0.3.0 ZIP预存与单附件上传

用户要求独立目录预存ZIP、后续只上传一个ZIP。默认目录为源码所在项目的 `data/app-upload-zips/`，可通过 `bundle_dir` 或 `CODEX_CHAT_ZIP_DIR` 指定。本项目在实际工作区的默认路径为 `~/process/app-upload-zips`；独立拷贝且无 workspace.json 时退回 `data/app-upload-zips`。

`prepare_upload_bundle(files, *, bundle_dir=None)` / CLI `prepare --file ... --file ... --bundle-dir ...`仅本地打包，无需App、不上传；返回zip_path/zip_sha256/size/entries/reused。包内保留原始文件及 `_upload_manifest.json` 的名称/大小/SHA-256，不附机器路径或旧回答。按材料内容指纹命名，同一组合复用同一包；内容变化产生新包，不覆盖旧包。校验后原子发布，损坏包拒绝复用。已有ZIP校验后预存/直接使用，不再套ZIP。

0.3.0起submit/ask/ask_once的files先打包，实际上传集合严格只有ZIP，回执保留包及单附件指纹；失败不回退散文件。可先prepare后files=[zip_path]。保留原始文件/旧包和未知回执，不自动批量删除。

```bash
PYTHONPATH=../../paper python3 -m codex_desktop_chat prepare --file /absolute/paper.pdf --file /absolute/visual.png
```

当时累计38项隔离测试通过，其他工作目录CLI本地打包通过。当前 `tests/` 静态计数为 50 个 `def test_`（未在本次文档修订中运行），以实际测试结果为准。没有新上传/消息；账户额度阻止继续有效。App ZIP上传/解压/图片与PDF读取尚未验收，不将历史PNG成功视为ZIP成功，不假定ZIP可绕过共享额度。主网页版制卡未改动。


## 2026-10-14 审计修复后的边界

包版本统一为1.0.0、Python最低3.11，接口协议和既有回执仍为1。所有UI变更需foreground=True，Python与Swift同时阻断未授权操作；collect保持只读。缓存命中核对本次源清单，已有ZIP核对整体SHA-256；并发发布不覆盖已有证据。verify_bundle新增manifest_files字段（无清单时为null）。符号链接及特殊条目拒绝。

收取按唯一请求锚点及下一用户轮次界定目标回答；多个无法分界的助手标题拒绝。完成标志必须处于该目标轮次，历史标志不能完成当前回答。暂缺锚点计入answer_timeout，只读等待，不重发。文本代码区保留；表格、图片、数学AX结构与重叠文本表示未验证时明确拒绝收取。文本坐标重建不能保证复杂公式排版保真。

回执阶段与转换受校验，终态不能倒退为提交。preparing/uploading崩溃后保留原记录及草稿，禁止自动核销、重发或按年龄删除；需要核对原进程、原窗口与材料证据。发送动作边界继续保守记录unknown，UI锁仅串行化协作调用，不能阻止用户干预。窗口PID/AX哈希不是正式Conversation ID，App重启后拒绝旧绑定。

不自动删除回执、原回答、冻结材料和未知请求；本项目当前保留政策优先于审计的一般清理建议。新建目录与临时文件采用受限权限，不自动修改历史目录权限。真实App并发、窗口身份稳定性、复杂内容及ZIP服务端读取仍未验收。
