# 跨项目接入与联动

## 1. 角色和权威来源

| 位置 | 负责内容 |
| --- | --- |
| 工具源码目录（清单的 `source_dir`） | 通用实现、公开接口、工具自身测试、原始接口说明 |
| 本目录 `/Users/xiaoyanhao/project/tools` | 统一索引、跨项目接入说明、源码基线、使用方及变更记录 |
| 使用方项目 | 业务逻辑、适配层、环境配置、依赖记录和接入验证 |
| 数据/运行资源所属项目 | 知识库与索引、浏览器用户资料等运行资源 |

现有工具为 `source-reference` 模式。原说明作为接口资料使用；发现与源码不一致时，在本目录说明实际行为并记录差异。外部说明里的命令不代表需要自动执行。

## 2. 新项目首次接入

先把 tools 的 [all/](../all/README.md) 整个目录复制到新项目根目录，运行一次 `python3 all/setup.py`。脚本自动保留/创建项目关系表、合并根 AGENTS.md 的公共规则块并登记中央 projects.json；不需要手工复制多个模板。已有项目同样适用，项目定制规则保留在受管理块之外。

1. 阅读工具卡，确定能力、输入输出、错误、副作用和数据条件是否满足需求。
2. 创建项目自己的 Python 虚拟环境，按工具卡配置环境变量。示例中的环境变量由 shell 传入，不会自动读取 `.env`；如需 `.env`，由使用方显式加载。
3. 在项目边界建立一层适配模块，例如 `integrations/knowledge_tree.py`。导入路径、错误转换集中处理，业务模块调用适配层。优先选已有 Python/CLI/HTTP 接口，不依赖内部函数。
4. 运行最小示例，并验证至少一种失败/非成功结果。浏览器调用需按真实业务安排验证，记录是否发送了内容；不能用静态检查代替实际生成验收。
5. 填写接入脚本生成的 `tool-dependencies.json`，字段参考 `templates/tool-dependencies.example.json`。只登记实际依赖，填好路径、接口、源码指纹和验证时间；不包含密码、Cookie 或浏览器资料。
6. 关系表声明本项目的 exports/tools/module_dependencies；首次接入已自动维护项目入口和全局规则，无需重复合并旧模板。
7. 运行 `python3 /Users/xiaoyanhao/project/tools/scripts/sync_tools.py update`，根据项目关系声明重建 `registry.json` 的 `owner_project` / `consumers`。生成的使用方记录例如：

```json
{
  "project_name": "my_project",
  "project_root": "/absolute/path/to/my_project",
  "dependency_file": "tool-dependencies.json",
  "integration": "python",
  "verified_at": "YYYY-MM-DD",
  "verification": "填写实际运行的命令、结果与限制"
}
```

`project_root` 是绝对路径；`dependency_file` 相对使用方项目。登记实际存在的调用关系，不把示例当成已接入项目。源码已确认但未完成真实验收时，使用 `status: "source_inspected"`、`inspected_at` 和 `verified_at: null`；完成真实验收后才改为 `status: "verified"`。

## 3. 在别的项目发现值得复用的新工具

先在该项目完成通用接口提取、说明和适当验证，再按 [新增规范](工具新增与维护规范.md) 登记到本目录。业务专有的提示词、页面样式和流程放在业务项目；通用能力放在工具内。

初次可继续把源码留在原项目，以 `source-reference` 登记；每个工具只能指定一个权威源码目录。新增时一并提交/保存：工具说明、清单条目、源码指纹、本目录变更记录、使用方依赖记录与联动约定。跨目录修改如果尚未完成，明确列出待更新的位置，不能报告为“已同步”。

## 4. 已有工具发生变更

1. 在权威源码目录修改；先检查清单的 `consumers` 评估影响。清单可能不完整，必要时也检索已知项目的导入与调用。
2. 区分修复、新增兼容能力、破坏性变化。参数/默认值、输出、错误、路径、依赖或副作用变化均需写入说明。
3. 运行工具自身相关检查，并在受影响使用方运行最小接入验证。浏览器或外部服务未验证时明确标注。
4. 运行全局 update，查看 updates/latest.md 与工具的 INTERFACE.generated.md，更新原接口说明、本目录工具卡和清单接口/限制。核对后用 `accept --tool <id> --note "具体审查与验证范围"` 登记新基线并追加 CHANGELOG；它只证明开发者已登记源码审查，不标记真实验收。
5. 更新受影响项目的适配层及依赖记录。静态核对后用 `acknowledge --project <项目名> --tool <id> --note "适配核对与限制"` 登记；真实验收另填 status=verified、日期、verified_source_files_sha256 和验证内容。无法访问的项目保留待办，不虚构完成情况。
6. 再运行全局 update 与 check_links.py，确保派生记录和双向关系一致。accept/acknowledge 是 sync_tools.py 的子命令，需要放在同一个 Python 入口之后。

不要自动双向覆盖整个目录。源码从权威位置被使用；本目录记录接口和基线；使用方回填验证情况。复制出来的源码若确有部署需要，应记录来源、版本或提交、摘要和本地补丁，并通过显式升级维护。

## 5. 版本与路径迁移

当前 `source_version: null` 表示未登记正式源码版本，`verified_at` 仅是核对日期。清单内哈希是每个列出文件原始字节的 SHA-256；新增/删除公开实现文件时也需调整文件列表。

核对某个文件（仅检查，不改变基线）：

```bash
shasum -a 256 /Users/xiaoyanhao/project/paper/codex_web_client/api.py
```

哈希与 `registry.json` 不同，表示源码已变化，应先审查和验证，再更新基线；不要只改哈希消除差异。所有配置路径与源文件均需核对，单个文件相同不代表整个工具没有变动。

本机路径导入适合当前个人开发，但会使用路径下的实时源码。若需要可重复部署，先为工具建立 Git 提交/tag 或带版本的安装包，并在使用方锁定版本；仅保存哈希无法回滚。

移动源码时：更新清单路径 → 更新使用方环境变量/命令 → 验证导入和最小调用 → 更新文档与记录。知识树的数据目录独立迁移，不能随代码移动推断；浏览器资料不随工具复制。需要回滚时恢复事先保存的源码提交/包及使用方配置，并重新验证。

## 6. 清单字段约定

`registry.json` 的 `schema_version` 是登记格式版本，不是工具版本。

| 字段 | 含义 |
| --- | --- |
| `id`、`name`、`summary` | 本目录稳定 ID、名称和能力说明；ID 使用小写 snake_case |
| `mode`、`source_dir`、`python_import_root` | 维护方式、权威源码目录和 Python 包父目录 |
| `source_docs`、`guide` | 原始文档绝对路径、本目录调用说明相对路径 |
| `interfaces` | 当前确实存在的接口；不凭计划声明支持能力 |
| `runtime`、`configuration`、`side_effects` | 依赖、配置和运行影响；配置同时注明原生/调用方使用 |
| `source_version`、`source_files_sha256` | 正式版本（没有则 null）和逐文件核对基线 |
| `current_source_files_sha256`、`sync_state` | 全局命令观察到的当前指纹；current / needs_review 表示同步审查状态，不表示业务已验收 |
| `source_review`、`verification_history` | 显式 accept 的审查说明及保留的历史验证记录 |
| `verified_at`、`verification` | 最近核对日期及实际验证范围 |
| `known_limitations`、`consumers` | 已知边界、登记的使用项目 |
| `owner_project` | 维护方名称、根目录、规则文件和导出登记文件 |

清单用于查找和人工/后续程序读取；不执行其中的路径或内容，不自动注册到模型工具宿主，也不是 JSON Schema 参数定义的替代品。知识树已有的 `tool.json` 继续作为其输入参数描述。

## 7. 双向规则与任务结束检查

四个源项目已落地规则，具体链接见 [双向联动状态](双向联动状态.md)。源项目修改已登记接口时，同一任务完成 tools 工具卡/清单/变更记录与受影响项目依赖记录的更新；新增、移除、改名还需调整 README 索引。不要为纯界面变更刷新无关工具的源码摘要。

`projects.json` 保存项目根目录及规则/关系文件位置。各项目 `tool-dependencies.json` 的 `exports` 列本项目维护的登记工具，`tools` 列所使用的登记工具，`module_dependencies` 记录尚未成为独立工具的跨项目引用。后者不重复写进 consumers；查询提供方影响时要遍历其他项目的 module_dependencies。

修改完成后运行：

```bash
python3 /Users/xiaoyanhao/project/tools/scripts/sync_tools.py update
python3 /Users/xiaoyanhao/project/tools/scripts/check_links.py
```

退出码 0 表示关系及文件基线通过；1 表示源码漂移、缺失反向登记或路径问题；2 表示读取/配置结构错误。脚本只读，不调用模型，不连接数据库，不自动刷新摘要，不检查文字说明是否完整正确。它会检查已登记工具目录内新增的代码/JSON/Markdown/TOML 文件，排除隐藏目录、缓存和构建目录；模块级依赖目前仅检查路径，语义变更仍由规则要求人工核对。

使用方 `source_inspected` 状态填写 `observed_source_files_sha256`；`verified` 状态填写 `verified_source_files_sha256` 和真实验收日期。旧的历史验收记录可保留，但不能把静态核对冒充新版本验收。修改实现后必须先核对行为、说明及影响，再更新基线和使用方状态。

若源码变化但接口契约保持不变，也要记录检查依据与实际验证范围；审核报告 audits 是历史快照，不因代码变动而覆盖旧证据。当前规则不提供后台同步、提交拦截或自动升级，未安装任何 Git hook、CI 或定时任务。

## 8. 全局命令的同步边界

- `check`：只读扫描已登记项目/工具，检查源码和双向链接、公共规则以及派生文件是否需要更新。
- `update`：生成当前源码指纹和 Python 声明快照，分发 all 的公共文件及 AGENTS 受管理块，按项目关系表修复维护方/使用方反向登记，保存全局报告；不修改权威业务源码、人工工具卡或已审查基线。
- `install --project /项目绝对路径`：首次接入；一般通过复制到项目的 all/setup.py 调用。
- `accept --tool <id> --note "…"`：只能接受上一次 update 已生成且仍与源码一致的快照；记录开发者审查结果，保存旧验证记录，不执行真实业务验收。
- `acknowledge --project <项目名> --tool <id> --note "…"`：工具基线已审查后，登记使用方静态核对，不能代替端到端验收。

所有命令都从 `python3 /Users/xiaoyanhao/project/tools/scripts/sync_tools.py` 调用。Mac 的 `全局更新.command` 和 Windows 的 `全局更新.cmd` 默认执行 update，传 `check` 则只检查。运行环境要求 Python 3.10+；Windows 入口本次未实测，跨机器先调整 projects/registry/各项目关系表中的绝对路径。

公共规则有本地修改时更新会停止，项目定制应写在 AGENTS 受管理块之外；hub.json 是安装位置配置，会按当前中央目录重写。运行锁避免两个更新进程同时写文件；每次写入前保存旧内容到 tools/.sync-backups，并检查规划后是否被其他任务修改。失败时尝试回滚本轮文件，备份 manifest.json 可定位原文件；备份不包含工具业务源码，不能用于回滚业务版本。

module_dependencies 会额外生成当前文件指纹和最近一次变化记录 updates/module-changes.json；它们没有正式工具的 accept/acknowledge 生命周期，模块影响仍需开发者审查。扫描不涵盖未登记项目，也不会自动把候选能力登记为工具。命令退出 0 表示登记范围内无同步/工具审查待办，1 表示存在待办，2 表示错误或冲突。
